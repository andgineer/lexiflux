# AI keys in the UI, per user, over the server's keys

## Overview

The llmbroker migration removed the AI settings page: lexiflux reads API keys only from the
environment and `.env`. That works for the author's laptop but not for a cloud setup, where a user
cannot change the server's environment. This plan brings the keys page back: every user enters their
own keys in the UI, llmbroker spends that user's keys for that user's calls, and the server's keys
(environment, `.env`) remain the fallback for users who have none.

## Decisions

| Topic | Decision |
|---|---|
| Keys page | An "AI keys" page in the UI for every user, in single-user and multi-user mode, linked from the navbar |
| Which keys | Every key lexiflux can use: the keys that serve the free pool (the refs `pool_keys()` returns, today Groq, Gemini, Z.ai) and the keys of the paid models' providers (OpenAI, Anthropic). The list comes from llmbroker, not from a hand-kept list in lexiflux |
| Hints | Each key's hint is llmbroker's own key info (`KeyInfo.help`, markdown with its link; its extras such as signup effort where useful), rendered on the page. lexiflux writes no provider instructions of its own |
| Per user | A user's key pays for that user's calls (llmbroker scope `u-<user id>`). A user without their own key uses the server's key from the environment or `.env` (llmbroker's scope fallback). The server's keys are never shown to users |
| Storage | lexiflux's database, encrypted at rest with a key derived from Django's `SECRET_KEY`. A saved key is never sent back to the browser: the page shows only that it is set and its last 4 characters. The user can replace or clear it. A key that can no longer be decrypted (changed `SECRET_KEY`) counts as not set |
| Status per key | The page tells the user where each key comes from: their own, the server's (without revealing it), or none |
| Takes effect | Saving or clearing a key takes effect on that user's next call, without a restart |
| Errors | The missing-key and rejected-key alerts link to the keys page and say whose key it was (the user's or the server's) |
| No manual steps | Nothing to run; the schema migration applies at start (`invoke run`, Docker start) |

## Phase 1 — Per-user keys behind llmbroker

- [x] Model for a user's key (user, llmbroker ref, encrypted value, updated at), unique per (user, ref);
  auto-generated migration. Encryption with a key derived from `SECRET_KEY` (Fernet or the like; add the
  dependency to `requirements.in` and `requirements.koyeb.in` only if it is not already installed,
  recompile without `--upgrade`)
- [x] A lexiflux secrets backend for llmbroker: scoped refs `u-<id>/<REF>` resolve from the database
  (decrypted); shared refs resolve as today (environment, then `.env`). Implement the enumerable protocol if
  llmbroker then avoids per-ref lookups; keep lookups cheap (no query per call once the ring holds the
  value). Wire it into `get_broker()`
- [x] Saving or clearing a key refreshes that user's scope so the next call uses the new state (find the
  llmbroker call that rebuilds or refreshes a ring; never restart the broker for it)
- [x] Tests: the user's key is used for their call; another user without a key gets the server's key; a
  cleared key falls back to the server's; a replaced rejected key is used again; blank input is not saved;
  an undecryptable value counts as not set; keys never appear in logs

## Phase 2 — The AI keys page

- [x] View, URL, template and navbar link, following the current UI patterns (`@smart_login_required`,
  CSRF, Vue with `[[ ]]` delimiters or the template style the other preference pages use now)
- [x] One row per key from llmbroker (pool keys, then paid providers), each with: a readable name, where
  the current key comes from (yours / the server's / none), the last 4 characters of the user's own key,
  llmbroker's hint rendered from markdown (links open in a new tab), a password input, Save and Clear
- [x] The saved value never goes back to the browser; the server's key never reaches any page
- [x] Tests: view tests (list, save, replace, clear, blank, another user's keys invisible, multi-user login
  required), and a Playwright or Selenium check of save and clear in the page

## Phase 3 — Errors point to the page

## Risks

- **`SECRET_KEY` rotation** makes saved keys unreadable; users see "not set" and enter them again
- **Server fallback in multi-user mode** lets users without keys spend the operator's keys, as today; an
  operator who does not want that leaves the server's keys unset
- **A stale key in the server's environment** wins over `.env` (llmbroker reads the environment first); a
  user's own key avoids it for that user
